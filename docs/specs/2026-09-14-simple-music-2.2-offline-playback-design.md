# Simple Music 2.2 离线与可靠播放设计

> 状态：单曲离线闭环已实现，自动化验证通过，跨平台人工验收待完成
>
> 目标版本：`2.2.0`
>
> 日期：2026-09-14
>
> 相关实现：`src/stores/player.ts`、`src/lib/audio-engine.ts`、`src/lib/playback-resolver.ts`、`server/lib/audio-cache.ts`、`server/routes/netease.ts`、`src/pages/SettingsPage.tsx`

## 1. 摘要

Simple Music 已经具备 2GB LRU 音频磁盘缓存：在线歌曲从头完整播放后会落盘，再次播放时由 `/api/audio` 命中本地文件。但这套能力目前仍是不可见的被动缓存，不能被用户主动保存，也不能保证断网可播：播放器总要先向平台解析一个临时播放 URL，之后才会带着 `cacheKey` 访问本地缓存。

2.2.0 将把这套基础升级为用户可理解、可控制的离线能力：

1. 在线曲目可以主动“离线保存”，也可以把已完整缓存的曲目固定保留。
2. 列表和播放器能展示曲目的离线状态，并允许单曲移除。
3. 播放前先查本地离线条目；命中时不登录、不联网、不解析上游 URL，直接播放本地文件。
4. 自动缓存仍受 LRU 上限约束；用户明确保存的离线文件不被自动淘汰。
5. 本地文件损坏或缺失时自动回到现有在线解析与跨源降级链路，不把离线能力变成新的单点故障。

本版本只交付单曲闭环。歌单批量下载、持久化下载队列、下载限速和独立下载中心延期，避免第一版同时引入大规模任务调度和复杂磁盘管理。

## 2. 背景与现状

### 2.1 已有能力

当前播放链路为：

```text
Track
  → PlaybackResolver 在线解析候选 URL
  → AudioEngine.load(URL, cacheKey)
  → /api/audio?url=<上游 URL>&cacheKey=<source:id:quality>
      ├─ 缓存命中：读取本地 .bin
      └─ 缓存未命中：代理上游，完整传输后原子落盘
```

已有缓存具备以下正确性基础：

- 文件名使用 `sha1(cacheKey).bin`，不会依赖短期有效的 CDN URL。
- 只缓存从 0 字节开始且覆盖完整文件的响应。
- 先写 `.part`，完成后再重命名为 `.bin`，中断播放不会留下可命中的半截文件。
- 命中时更新 mtime，超限后按 LRU 淘汰。
- 设置页可查看总容量和文件数、修改目录与上限、清空全部缓存。
- 试听片段和无稳定缓存身份的直链不会落盘。

### 2.2 当前问题

1. **断网仍不能播放缓存**：`player.loadTrack()` 会先进入 `PlaybackResolver`；平台接口不可达时拿不到临时 URL，也就到不了 `/api/audio` 的缓存命中分支。
2. **用户不知道哪些歌可离线播放**：缓存只有哈希文件，没有曲名、封面、原始曲目身份、真实播放来源和音质等可展示元数据。
3. **用户无法保留喜欢的缓存**：所有文件都受同一 LRU 规则约束，可能在不知情时被淘汰。
4. **只能全清，不能单独管理**：没有批量状态查询、单曲删除、固定或取消固定能力。
5. **跨源缓存缺少归属关系**：QQ 内容可能实际使用网易云音频，文件 key 跟真实候选走，但用户再次打开的是原始 QQ 曲目；系统需要记住两者之间的本次离线绑定。

## 3. 产品目标与非目标

### 3.1 目标

1. 用户能对任一在线曲目执行“离线保存”，完成后获得明确反馈。
2. 已经被动完整缓存的曲目可以直接转为“离线保留”，无需重复下载。
3. 离线条目可按原始曲目 `(source, id)` 查询；即使实际音频来自另一平台，也能从原入口命中。
4. 离线文件命中优先于平台登录态、启用状态和在线解析。
5. 自动缓存与离线保留拥有清晰、不同的容量和清理语义。
6. 所有新增异步流程支持取消与迟到响应丢弃，不干扰当前播放会话。
7. 老用户升级后不清空已有缓存，现有播放和设置行为保持兼容。

### 3.2 非目标

2.2.0 首版明确不做：

- 歌单、专辑或“我喜欢”的批量离线保存。
- 应用重启后自动续传未完成任务。
- 多任务并发、下载优先级、限速、定时下载或仅 Wi-Fi 下载。
- 把离线文件导出为普通音频文件，或写入 ID3 标签、封面和歌词。
- 对本地音乐提供“离线保存”；它们本来就是本地文件。
- 跨设备同步离线文件或离线状态。
- 绕过平台会员、付费、试听、版权或地区限制。
- 在本轮实现 QQ 红心/歌单写入、MV、评论页或补丁热更新。

## 4. 核心产品决策

### 4.1 区分“自动缓存”和“离线保留”

| 状态 | 含义 | 会被 LRU 淘汰 | 清理临时缓存时删除 |
|---|---|---:|---:|
| 未缓存 | 本地没有完整音频 | — | — |
| 保存中 | 正在主动获取完整音频 | — | — |
| 已缓存 | 播放产生的完整临时缓存 | 是 | 是 |
| 离线可用 | 用户明确保存或固定保留 | 否 | 否 |
| 保存失败 | 本次保存失败，可重试 | — | — |

“已缓存”只表示当前本地恰好存在，不能承诺长期保留；“离线可用”才是稳定承诺。界面不得把两者都笼统写成“已下载”。

### 4.2 离线命中优先于在线解析

在线曲目的新播放顺序为：

```text
用户选择 Track
  → 按原始 source:id 查询可用离线条目
      ├─ 命中：/api/audio-cache/file?entryId=... 直接加载
      │    ├─ canplay：提交离线播放来源和实际音质
      │    └─ media error：标记条目异常，继续在线解析
      └─ 未命中：进入现有 PlaybackResolver
```

因此：

- 平台退出登录、暂时被禁用或网络断开时，已经保存的曲目仍能播放。
- 离线条目只改变“从哪里取得音频”，不改变 `Track.source`、队列、歌词和页面归属。
- 离线文件缺失或文件大小与索引不符时修正索引；媒体加载错误只在本次播放会话跳过该条目，不自动删除用户固定的文件。在线可用则继续原有同源降级和跨源兜底。

### 4.3 主动保存沿用当前播放策略

“离线保存”不新增另一套音源配置。保存时读取当下的：

- 音质偏好；
- 原音源优先设置；
- 播放音源顺序；
- 跨平台自动换源设置；
- 平台登录与启用状态。

系统使用独立的离线保存会话复用 `PlaybackResolver` 的候选生成与跨源匹配，但不占用、不暂停、也不修改 `AudioEngine` 和当前播放状态。首个能完整下载且不属于试听的候选成为离线条目；失败时继续下一个候选，直到成功、取消或候选耗尽。

### 4.4 离线文件保留真实来源

每个条目同时记录：

- `originRef`：用户操作的内容曲目，例如 `qq:003...`；
- `resolvedRef`：实际提供音频的曲目，例如 `netease:123...`；
- `quality`：实际交付音质，而不是请求档位；
- `cacheKey`：继续使用真实候选的 `source:id:quality`。

界面在必要时可显示“离线音频来自网易云”，但默认仍展示原曲目的名称、歌手和封面。离线播放不冒充内容来源，也不执行在线听歌打卡。

### 4.5 注销账号不自动删除离线文件

离线文件属于本机数据。退出平台账号或停用音源后仍保留，用户可在单曲菜单或设置页主动移除。设置页退出登录提示中应说明离线内容不会随账号注销自动清理。

## 5. 离线索引模型

现有 `.bin` 文件无法支撑枚举、跨源归属、固定状态和内容类型。服务端新增版本化索引：

```ts
interface AudioCacheIndexV1 {
  schema: 1
  entries: Record<string, AudioCacheEntry>
}

type AudioCacheEntry = ManagedAudioCacheEntry | LegacyAudioCacheEntry

interface CacheFileEntry {
  entryId: string
  fileName: string
  size: number
  createdAt: number
  updatedAt: number
}

interface ManagedAudioCacheEntry extends CacheFileEntry {
  legacy?: false
  cacheKey: string
  contentType: string
  origins: Array<{
    source: 'netease' | 'qq'
    id: string
    name?: string
    artist?: string
    album?: string
    cover?: string
    duration?: number
    lastUsedAt: number
    savedAt?: number
  }>
  resolved: {
    source: 'netease' | 'qq'
    id: string
    name?: string
    artist?: string
    album?: string
    cover?: string
    duration?: number
  }
  quality: string
}

interface LegacyAudioCacheEntry extends CacheFileEntry {
  legacy: true
}
```

约束：

- 受管条目的 `entryId` 使用 `sha1(cacheKey)`，与音频文件基名一致；旧缓存扫描只从现有文件名取得 `entryId`，不伪造无法反推的 `cacheKey/resolved/quality/contentType`。
- `source` 和 `id` 入库前一律 `String()` 并校验，禁止把任意路径当身份写入。
- `fileName` 只能由服务端生成，客户端不能提交磁盘路径。
- 一个实际缓存文件只对应一个 `entryId`，但 `origins` 可以保存多个原始入口；同一个跨源音频被不同入口复用时合并别名，不覆盖旧入口，也不建立全局歌曲实体。
- 离线保留是别名级状态：某个 `origin.savedAt` 存在，表示用户从该原始入口明确保存；只要任一别名仍有 `savedAt`，该物理文件就不能被 LRU 淘汰。
- `origins` 按 `(source, id)` 去重。用户主动保存的别名绝不自动丢弃；未保存别名最多保留最近使用的 8 个，避免错误匹配或长期运行导致单条记录无界增长。
- `name/artist` 对被动缓存可为空；主动保存或固定时由客户端随 `origin` 补齐。状态查询保持只读，不承担元数据回写。
- 索引写入使用同目录临时文件加原子 rename，并通过模块级串行队列避免并发覆盖。
- 索引保留一个最近有效备份。主文件损坏时先恢复备份；两份都不可读时，把未识别 `.bin` 计入“待识别数据”，禁止 LRU 和临时清理自动删除，由用户显式处理。

新产生的被动缓存也必须写索引。`AudioEngine.load()` 向 `/api/audio` 传递最小缓存上下文（原始 `source/id`、真实候选 `source/id` 和实际音质），服务端在完整文件提交时同时 upsert 索引；曲名、歌手等展示信息可在用户主动保存或固定时补齐。上下文只包含领域标识，不允许包含文件路径。

### 5.1 并发与文件一致性

仅把索引 JSON 串行写入不足以保护音频文件。缓存模块统一采用两层协调：

1. **目录级维护门闩**：普通播放、被动缓存和主动保存登记活动租约；清理、目录迁移和索引灾难恢复先关闭新租约入口，再限时等待已有任务结束。超时则返回 `CACHE_BUSY`，本次不修改配置或文件。
2. **`originKey` 级互斥锁**：主动保存完成、固定和取消固定先锁住原始 `(source, id)`，保证同一原始曲目不能并发写出多个 `savedAt`。
3. **`entryId` 级读写锁**：文件播放持有读锁；同一条目的被动写入、主动保存、固定状态变更和删除持有写锁；不同条目仍可并行。LRU 只尝试获取候选条目的写锁，忙碌条目直接跳过，并在删除前重新核对别名保存状态。

锁顺序固定为“目录活动租约 → origin 锁 → 按 `entryId` 排序的条目锁 → 索引写队列”，不涉及 origin 的文件播放/LRU 可跳过 origin 锁，但禁止反向获取。每次写入使用带任务 ID 的独立 `.part`，提交前再次确认条目未被删除、目录未迁移。Windows 上播放流持有条目读锁直到 stream close；删除、清理、LRU 和目录迁移不能无限等待，也不能让索引先指向一个尚未删除成功的状态。

## 6. 服务端能力

### 6.1 状态查询

```text
POST /api/audio-cache/status
body: { tracks: [{ source, id }] }
```

返回每首曲目的 `missing / cached / pinned`、`entryId`、实际来源、音质、大小和 `savedAliasCount`。`pinned` 表示请求的这个 `source:id` 别名已被用户保存，`savedAliasCount` 表示共享文件上仍有多少个已保存别名。接口必须支持批量查询，列表组件不得逐行发请求；单次上限建议 100 个，超出由调用方分批。

查询只读索引与文件状态，不触发平台请求，不更新 LRU mtime。真正播放本地文件时才续期自动缓存。

### 6.2 本地文件播放

```text
GET /api/audio-cache/file?entryId=<sha1>&originSource=<source>&originId=<id>
```

- 只根据索引解析服务端生成的文件名，不接受路径和上游 URL。
- `originSource/originId` 必须匹配条目中的一个别名，用于更新正确别名的最近使用时间；不匹配返回 404，不能借此探测其他缓存条目。
- 沿用 `serveFileWithRange()`，支持拖动进度和 Chromium 的 Range 请求。
- 使用索引里的 `contentType`，不再依赖临时上游 URL 推断格式。
- 文件不存在时返回 404，并移除失效索引条目。
- 成功打开文件时更新文件 mtime 和命中别名的 `lastUsedAt`；状态查询本身不续期。

### 6.3 主动保存

```text
POST /api/audio-cache/save
body: {
  url,
  cacheKey,
  origin,
  resolved,
  quality,
  trial
}
```

- `url` 必须继续通过 `isSafeUpstreamUrl()`，请求头复用 `audioProxyHeadersFor()`。
- `cacheKey` 必须由服务端按 `resolved.source:id:quality` 重算或严格核对，不能信任任意字符串。
- 渲染层不得为 `trial: true` 的候选调用保存端点；服务端同时拒绝显式试听候选。该字段是本机可信客户端的结构保护，不宣称能仅凭 CDN URL 重新判断平台版权属性。
- 主动保存采用比被动缓存更严格的完整性检查：只接受带正数总长度的 200，或 `Content-Range` 明确覆盖 `0..N-1/N` 的 206；实际写入字节数必须等于声明总长度。响应还必须是已知 `audio/*` MIME，或能通过受支持音频格式的文件头识别，避免把 HTML 错误页固定为音频。
- 写入继续使用 `.part → .bin` 原子流程；客户端断开或请求取消时停止上游读取并删除 `.part`。
- 如果相同 `entryId` 已完整存在，只补齐索引并给本次 `origin` 写入 `savedAt`，不重复下载。
- 如果相同文件已有其他 `origin`，把本次入口合并进 `origins`。重新保存同一原始曲目成功后，原子清除它在其他条目上的 `savedAt`，保证每个原始曲目只有一个明确的离线版本。
- 重新绑定是跨条目事务：下载成功后先获取该 `originKey` 锁，再从索引收集含该 `origin` 的全部条目，按 `entryId` 排序获取写锁，锁内重新查询并一次提交索引；不得在下载开始前清除旧 `savedAt`。其他保存与 `pin` 同样受 origin 锁约束，因此锁集合建立期间不会新增该 origin 的已保存条目。
- 该请求允许使用比全局 30 秒更长的超时；第一版只展示“保存中”，不承诺百分比进度。

### 6.4 固定、取消固定与删除

```text
POST /api/audio-cache/pin     body: { entryId, origin, pinned }
POST /api/audio-cache/delete  body: { entryId, origin, confirmShared?: boolean }
POST /api/audio-cache/clear   body: { scope: 'temporary' | 'pinned' | 'unmanaged' | 'all' }
```

- 固定只允许操作条目中已经存在的 `origin` 别名，为其新增或更新 `savedAt`，并可补齐展示元数据，不复制文件；新别名只能由实际播放提交或主动保存流程建立。
- 取消固定只清除指定别名的 `savedAt`；仍有其他已保存别名时，共享文件继续受保护。所有别名都未保存后，文件变回普通缓存并参与下一轮 LRU，但不当场删除。
- 单曲删除是文件级操作，会移除对应 `.bin/.part` 和所有别名。若除了请求 `origin` 外仍存在任何已保存别名，且未传 `confirmShared`，服务端返回 409 `CACHE_SHARED` 和最新数量；界面提示影响范围并二次确认后重试，避免仅依赖可能过期的状态查询结果。
- 文件级删除先从索引快照取得全部已保存 origin，按 `originKey` 排序加锁，再获取条目写锁并重新核对；别名集合变化则释放后重试，不能越过未持有的 origin 锁修改其离线承诺。
- 批量清理按 scope 执行；`pinned` 与 `all` 必须由界面二次确认。文件删除失败时不先宣告成功，索引与磁盘保持可重试的一致状态。

### 6.5 容量与清理

`GET /api/audio-cache/stats` 扩展为：

```ts
{
  bytes: number
  files: number
  temporaryBytes: number
  temporaryFiles: number
  pinnedBytes: number
  pinnedFiles: number
  unmanagedBytes: number
  unmanagedFiles: number
  limit: number
  dir: string
}
```

现有“缓存上限”改名为“临时缓存上限”，只约束没有任何 `savedAt` 的条目。LRU 淘汰必须跳过含已保存别名的文件和待识别文件。设置页提供：

- “清理临时缓存”：只删除未固定文件；
- “移除全部离线内容”：单独入口，二次确认后删除固定文件；
- “清理待识别数据”：只在索引灾难恢复后出现，说明来源并要求显式确认；
- 总占用、临时缓存和离线内容的分项统计。

若固定文件本身已超过临时缓存上限，不自动删除，也不阻止播放；界面仅提示离线内容由用户自行管理。

## 7. 渲染层状态与交互

### 7.1 离线状态 store

新增轻量 `offline-cache` store，负责：

- 按 `source:id` 缓存状态；
- 批量查询可见列表中的曲目；
- 管理单个主动保存会话和取消控制器；
- 保存、固定、取消固定、删除后的局部状态更新；
- 用任务 ID 丢弃取消后的迟到结果；保存任务独立于当前播放和页面组件，切歌、切页面后继续执行，只有用户明确取消或应用退出才中断。

第一版全局同时只允许一个主动保存任务。已有任务时新的保存请求保持可见但不可启动，并提示等待或取消当前任务，不通过暗中取消前一个任务来制造“最后一次点击生效”的错觉。

状态查询结果可短时缓存，但文件变更后必须主动失效；不得把整个服务端索引复制进 localStorage 形成第二事实来源。

### 7.2 入口

2.2.0 只增加以下入口：

1. `TrackRow` 的更多操作：未缓存显示“离线保存”，已缓存显示“保留离线”，已固定显示“取消离线保留”；有本地副本时另提供“删除本地副本”。
2. 播放器当前歌曲的更多菜单提供相同操作。
3. 已缓存/已固定曲目使用克制的状态图标；图标必须有 tooltip 和无障碍名称，不能只靠颜色区分。
4. `AppShell` 提供全局单任务状态条，展示曲名、保存中/完成/失败和取消入口；切换页面后任务仍可见。
5. 设置页只做容量分项与清理，不新增独立下载中心。

列表首次渲染不能因为离线查询阻塞正文。状态图标迟到出现时不改变行高和主操作位置，避免列表跳动。

### 7.3 文案

- 主动保存成功：`已保存，可离线播放`
- 被动缓存转固定：`已保留，不会被自动清理`
- 取消固定：`已改为临时缓存，空间不足时可能被清理`
- 删除共享文件：`此文件还被其他离线条目使用，删除后它们也将不可离线播放`
- 受限歌曲：直接复用现有登录、会员、付费、试听或版权限制提示
- 磁盘不足：`保存失败：磁盘空间不足`
- 网络中断：`保存中断，可稍后重试`
- 本地文件损坏但在线兜底成功：`离线文件不可用，已切换为在线播放`

## 8. 播放与保存的边界行为

### 8.1 同一曲目的多个本地候选

状态查询和播放必须使用同一套确定性选择规则：

1. 优先选择请求别名上带 `savedAt` 的条目；正常情况下主动保存会保证只有一个。
2. 没有主动保存条目时，优先选择 `resolved.source === origin.source` 的自动缓存。
3. 仍有多个候选时选择最近成功使用的条目，再以 `entryId` 排序保证结果稳定。

重新保存成功后才清除该原始曲目在旧条目上的 `savedAt`；新保存失败不得破坏旧离线版本。文件被其他别名共享时，只取消当前别名的离线保留不会删除物理文件。

### 8.2 音质

- 主动保存使用操作发生时的全局音质偏好，最终记录上游实际交付音质。
- 已有离线条目优先播放，不因用户之后修改全局音质而重新下载。
- 用户选择“重新保存当前音质”属于后续增强；2.2.0 先要求移除后重新保存。

### 8.3 跨源

- 离线状态跟原始曲目入口绑定，文件 key 跟实际播放候选绑定。
- 主动保存允许沿用跨源兜底；成功提示中若发生换源，应显示实际来源。
- 播放离线条目时 `actualSource` 使用 `resolved.source`，来源徽标继续如实展示。
- 离线播放不再次搜索“更优”来源，保证零网络依赖和稳定启动。
- player store 新增 `playbackTransport: 'online' | 'offline' | 'local'` 和 `offlineEntryId`。离线命中提交 `actualSource/currentQuality`；索引含完整真实曲目快照时同时提交 `resolvedTrack`，否则保持 `resolvedTrack: null`，不得用原始曲目元数据伪造真实候选。
- `maybeScrobble()` 只允许 `playbackTransport === 'online'` 时上报。离线播放即使账号仍登录、平台仍启用，也不向任一平台提交听歌记录。

### 8.4 登录、停用与断网

- 离线预检发生在 provider 参与状态判断之前。
- 保存动作仍要求至少一个在线平台已登录并启用。
- 退出登录、停用平台、应用重启或系统断网不影响已经固定的离线文件。
- 歌词仍沿用现有在线获取和本地同名歌词能力；2.2.0 不承诺在线歌曲歌词离线可用。

### 8.5 试听与版权限制

- `trial: true` 的候选不能主动保存，也不能被标成“离线可用”。
- 能确认 `trial` 的条目不得迁移为固定内容。`legacy` 条目没有试听标记时不能直接固定，必须先经一次在线候选解析确认非试听并补齐受管索引。
- 候选解析返回会员、付费、登录或版权限制时，保存流程与播放流程使用同一分类提示，不包装成笼统的“下载失败”。

## 9. 兼容与迁移

升级到 2.2.0 时：

1. 不删除旧 `.bin` 缓存，也不改变缓存目录和容量配置。
2. 首次建立索引时扫描旧 `.bin`，为其创建 `legacy: true`、`origins: []` 的临时条目并记录迁移标记；旧文件继续按 mtime 参与 LRU，但不会伪装成可识别的离线内容。
3. 当旧缓存被一次已知 `cacheKey` 命中时，补齐 `resolved/quality/contentType` 和原始别名，清除 `legacy`，使其进入可见管理范围。
4. 每次成功写索引时保留最近有效备份。主索引损坏先恢复备份；主备均损坏且迁移标记已存在时，未识别 `.bin` 进入保守隔离，不参与 LRU 或临时清理，并计入设置页“待识别数据”。
5. 索引损坏不能阻止应用启动、离线文件保护或在线播放；用户可显式清理待识别数据，系统不得替用户猜测哪些文件曾被固定。
6. 改变缓存目录时沿用当前语义：旧目录中的缓存会被清理。若旧目录含离线保留内容，操作前必须明确提示并二次确认，不能静默删除。

## 10. 实施范围

预计改动集中在：

- `server/lib/audio-cache.ts`：索引、固定语义、单曲管理、LRU 调整、主动保存。
- `server/routes/netease.ts`：将通用音频缓存管理路由拆出或继续集中挂载；新增状态、文件、保存、固定和删除端点。
- `src/lib/audio-engine.ts`：支持加载不含上游 URL 的本地缓存端点，现有本地 API 直连规则可复用。
- `src/stores/player.ts`：在线解析前的离线预检、离线候选提交、损坏后的在线回退。
- `src/stores/offline-cache.ts`：状态查询与单曲保存会话。
- `src/lib/api.ts`：让 `api.post()` 与 `api.get()` 一样接收 `AbortSignal`，主动取消时真正中止服务端请求。
- `src/components/Explore/TrackRow.tsx`、`src/components/Player/MoreMenu.tsx`：单曲入口与状态。
- `src/components/Layout/AppShell.tsx`：跨页面可见的单任务状态与取消入口。
- `src/pages/SettingsPage.tsx`：容量分项、临时清理、离线内容清理确认。
- `docs/playback-system.md`：实现完成后同步最终链路和缓存语义。

如果路由继续放在 `server/routes/netease.ts` 会让通用缓存能力长期挂在网易模块名下，实施时优先评估抽成独立 `server/routes/audio-cache.ts`；只做文件移动，不趁机重构其他网易路由。

## 11. 验收标准

### 11.1 单曲保存

- 未缓存在线歌曲可主动保存，成功后显示“离线可用”。
- 已完整缓存歌曲执行保存时不重复拉取音频，只转为固定状态。
- 保存过程不暂停、不切换、不重置当前播放曲目与进度。
- 连续点击、取消、切页面或关闭应用不会留下可命中的半截文件。
- 试听、会员、付费、登录失效和版权限制分别显示已有的具体原因。

### 11.2 离线播放

- 完全断网后，从列表、队列、最近播放和恢复态播放已保存曲目均能出声。
- 对应平台已退出登录或被停用时，已保存曲目仍可播放。
- 跨源保存的曲目从原始入口能命中，并展示真实音频来源。
- 离线文件缺失或大小不符时修正索引；媒体加载错误只跳过本次离线候选，不自动删除固定文件；在线可用则回到现有解析器。
- 离线播放支持断点、拖动、暂停、倍速、上下曲和 Media Session。
- 离线播放不会触发网易云或 QQ 的听歌打卡；切到下一首在线曲目时也不会补报上一首离线播放。

### 11.3 管理与容量

- 列表批量查询不会产生 N+1 请求。
- 固定文件不会被 LRU 或“清理临时缓存”删除。
- 取消当前别名的固定后，若没有其他已保存别名，文件才参与 LRU；单曲删除后所有共享别名、统计和磁盘一致。
- “移除全部离线内容”和含离线文件的缓存目录迁移都必须二次确认。
- 索引损坏、文件孤立、磁盘只读和空间不足不会导致服务或播放器崩溃。

## 14. 风险与待确认项

### 14.1 主要风险

- 上游 URL 和响应行为不稳定，后台完整下载必须复用现有多候选与超时策略。
- 固定文件不受 LRU 约束，磁盘占用可能持续增长，设置页必须明确展示和提供安全清理。
- 跨源绑定若只按标题猜测会播放错版本；必须复用现有保守匹配结果，不自行放宽匹配标准。
- Windows 上文件正在播放时删除或迁移目录的行为与 macOS 不同，需要显式处理占用失败。
- 旧缓存没有元数据，迁移只能渐进完成，不能承诺升级后立刻列出全部历史缓存。

### 14.2 实施前默认决策

若没有新的产品反馈，实施按以下默认值推进：

- 2.2.0 只做单曲，不做批量。
- 主动保存使用当前全局音质和播放来源策略。
- 离线命中永远优先于联网解析。
- 注销或停用平台不删除离线文件。
- 自动缓存可以固定；固定后不受临时缓存上限约束。
- 第一版只有“保存中”，不做百分比进度和断点续传。
