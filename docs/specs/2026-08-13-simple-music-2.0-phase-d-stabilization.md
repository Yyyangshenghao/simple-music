# Simple Music 2.0 阶段 D：稳定与迁移

> 日期：2026-08-13
> 状态：代码、全量自动化与生产构建已通过；真实双账号核心人工矩阵已通过，仍暂不提升版本号。

## 1. 本阶段目标

阶段 D 收敛 1.x 的二选一音源模型，保证旧设置和混合播放队列可迁移，同时让账号核实、禁用平台与恢复播放之间没有隐式请求或交叉覆盖。

## 2. 已实现决策

### 2.1 旧设置只读迁移

- `settings` store 不再包含或写回 `activeSource`、`crossSourceFallback`。
- provider 初始化直接读取 `simplemusic-settings` 原文，只提取上述两个 1.x 字段作为一次性迁移输入。
- 首次写入新 provider schema 前，把完整 1.x 原文备份到 `simplemusic-settings-v1-backup`；已有新 schema 时不重复迁移。
- 通用设置变化不再反向改写平台启用状态或播放优先级。

### 2.2 账号状态独立核实

- 网易云与 QQ 的启动登录状态请求分别更新自己的 provider，不通过共享布尔值订阅互相推断。
- 登录成功与退出登录同时更新兼容 UI 状态和 provider 运行态。
- 写操作收到 401 时把对应 provider 标记为 `expired` 并自动停用；另一平台保持不变。
- API 边界会把全部平台请求的 401/403 统一同步到鉴权失效入口，因此即使业务为容错而吞掉错误，也不会留下“仍显示已登录”的错位；普通网络失败和本地 API 鉴权错误不会误伤音乐账号。

这解决了一个迁移期竞态：若两个登录状态请求分批返回，先返回的平台不再把另一个尚未核实的平台误判为退出。

### 2.3 显式平台绑定

- 用户歌单加载必须传入 `ProviderId`，晚到结果由会话号丢弃。
- `useMusicService` 不再读取全局状态，只接受显式 `source`；实体查询统一以实体来源为准。
- 删除二元 `otherSource()` 默认推断，旧匹配入口如仍调用必须显式传目标平台。
- PlayerStore 删除兼容 `fallbackSource`，实际来源只认 `actualSource` / `resolution`。

### 2.4 播放恢复 schema 2

- 新存档写入 `schema: 2`；兼容读取 1.x 无 schema 队列，拒绝未知 schema。
- 过滤来源或基础身份损坏的曲目，并按原始对象重新定位队列下标。
- 混合队列恢复为暂停态，保留内容来源但清空实际播放来源；恢复过程不解析 URL，也不访问平台。
- 再次播放时按当前已登录且已启用的平台重新建立解析会话。

### 2.5 首页请求节流与可诊断失败

- 相同“平台 + 数据面”的并发只读请求复用同一个在途任务，成功结果短暂缓存 15 秒，减少混合/单平台切换造成的重复上游请求。
- 用户主动重试会绕过已完成缓存，但连续重试仍合并在途任务。
- 平台启用或账号状态变化立即清除该平台缓存，避免跨账号复用。
- 各平台栏目继续独立落地成功、空数据与结构化错误；错误原因会脱敏后保留用于诊断，用户文案不暴露 cookie、token 或上游 URL。

## 3. 自动化覆盖

- 四种 1.x 平台/降级组合迁移、坏 JSON、未知 provider schema、重复初始化和原文备份。
- 用户歌单显式平台路由、失败与跨平台晚到结果。
- 1.x 混合队列恢复、schema 2 循环、坏条目过滤、未知 schema 拒绝。
- 登录过期同步 provider 状态；平台启动状态独立。

## 6. 回滚与剩余风险

- provider 新设置和 1.x 原文备份使用不同 key，回滚 1.x 时可从备份恢复，不依赖 2.0 schema。
- 播放存档未知 schema 选择“不恢复”而非猜测，最多丢失上次队列，不会自动请求错误平台。
- 非官方上游接口、真实 VIP/版权限制与媒体解码失败只能通过真实账号样本补齐，自动化不能替代。
