# QQ 歌单 Web 写接口公开源码研究

研究日期：2026-10-16（Asia/Shanghai）。仅下载官网公开前端源码、维护者仓库；仅对官网首页公开歌单执行匿名读取。未查看登录 Cookie，未调用任何写入接口。

## 结论

- 已证实官网存在 `music.musicasset.PlaylistBaseWrite/EditPlaylist`，支持名称和其他元数据编辑。
- 已证实创建 `AddPlaylist` 可传 `dirShow:2`（仅自己可见），`1` 为所有人可见。
- 未找到歌曲顺序写接口；不能保证精确顺序。`orderlist` 是详情读取参数，不能当成写入。
- 方法存在不等于当前无签名 musicu Web Cookie 写通道成功。仓库已有2026-08-30写入业务码80105的实测事实；本轮未改变此结论。

## 创建 / 编辑精确参数

来源：common 调用的 RPC 封装；edit 的 publishPlaylistInfo 调用。

```ts
// AddPlaylist（官网编辑页创建分支）
{ dirName, dirDesc, dirPicUrl, taglist, dirShow }
// EditPlaylist（官网编辑页现有歌单分支）
{
  dirId: playlistInfo.dirid,
  mask: 95,
  dirNewName: editInfo.title,
  dirNewDesc: editInfo.content,
  dirNewPicUrl: editInfo.cover === defaultCover ? "" : editInfo.cover,
  dirNewPicUrl2: editInfo.cover2 === defaultCover ? "" : editInfo.cover2,
  dirNewtaglist: editInfo.tags.map(tag => tag.id).join(","),
  dirShow: editInfo.dirShow
}
```

隐私值直接证据：edit 定义 `SHOW=1,HIDE=2`，radioData 为 `{id:1,text:"所有人可见"}` / `{id:2,text:"仅自己可见"}`。编辑初始值从 `dirinfo.dir_show` 读取。playlist 对 `owndir===0 && dir_show===2` 显示“此歌单已被创建者设为隐私”。

只证实 `mask:95` 的全字段编辑请求，未证实单名称 mask。不要猜 `mask:1`；如实现改名，先读回并保留 desc/picurl/picurl2/tag/dir_show 等字段，避免清空其他元数据。官网编辑页拒绝 dirid 201..206；名称 trim 后非空、最多20 JS字符，描述最多2000字符。

官网 edit 用 `music.srfDissInfo.aiDissInfo/uniform_get_Dissinfo` 参数 `{dirid,optype:3,tag:1,userinfo:0,pic_dpi:300}` 读取编辑元数据并取 `data.dirinfo`。官网只检查 EditPlaylist 子块 code=0 的 bool；不能由此断言响应有/没有 retCode，应按实际多层code校验并读回确认。

## 歌单身份与归属（匿名只读实测）

从官网首页真实公开推荐歌单取 disstid=7891591354，用不带 Cookie 的一次 musicu 请求比较：
- `music.srfDissInfo.DissInfo/CgiGetDiss`（现有仓库方法）
- `music.srfDissInfo.aiDissInfo/uniform_get_Dissinfo`（官网方法）

二者外层 code、目标块 code、data.code 均为0，dirinfo 结构一致：

```text
dirinfo.id: number = 7891591354（公开歌单tid；该响应没有tid字段）
dirinfo.dirid: number = 51（内部目录ID；不能由公开tid替代）
dirinfo.host_uin: number
dirinfo.creator.musicid: number
dirinfo.owndir: number = 0（匿名用户不是所有者）
dirinfo.dir_show: number = 1
dirinfo.title/desc/picurl/picurl2: string
dirinfo.tag/vec_tagid/vec_tagname: array
```

官网把 `!!dirinfo.owndir` 作为拥有者标记。实现建议同时核对账号关联、`owndir===1` 与 `creator.musicid`；这属于安全实现建议，不是本次登录态验证结果。

## 官网请求信封与限制

vendor 的公共参数：

```ts
{ cv:4747474, ct:24, format:"json", inCharset:"utf-8",
  outCharset:"utf-8", notice:0, platform:"yqq.json", needNewCode:1,
  uin:getUin()||0, g_tk_new_20200303:getACSRFToken(true),
  g_tk:getACSRFToken() }
```

官网 `needNewCode` 为 camelCase；仓库历史文档/维护者库使用 `need_new_code`。本轮没单独比较该差异。官网 Web comm 中未发现 `authst`；不能称它是官网必需项。仓库可保留现有鉴权兼容层，但不应把其等同官网当前完整请求。

getACSRFToken 初值5381，逐字符 `h += (h << 5) + charCode`，末尾 `& 0x7fffffff`。true 模式优先 `qqmusic_key || p_skey || skey || p_lskey || lskey`，默认模式优先 `skey || qqmusic_key`；因此有 skey 时两个token可能不同。官网 vendor 没有直接从 qm_keyst 计算token，common 的登录key helper会回退 qm_keyst。

官网 RPC 包装器将请求放入 comm + req_N，外层 code非0拒绝，子响应按相同 req_N回填；withCredentials=true。更关键的是当前 vendor 默认 `needSign:true`，浏览器分支先 getSecuritySign(JSON)，再 encrypt(JSON)，把 musicu.fcg 改为 musics.fcg，查询参数 `encoding=ag-1,sign=...`，Content-Type=text/plain，响应arraybuffer。因此本次仅证明 API形状，不能证明现有plain musicu写通道可用，更不能将80105直接解释为某个特定鉴权错误。

## tags / 默认封面补充

匿名公开歌单实际存在方法差异：CgiGetDiss返回 `tag:[]`、`vec_tagid:number[]`（长度3）、`vec_tagname:[]`；uniform_get_Dissinfo返回 `tag:Array<{id:number,name:string}>`（长度3）、`vec_tagid:number[]`（长度3）、`vec_tagname:[]`。官网编辑初始化使用 `tags:r.tag||[]`；提交用 `tags.map(tag=>tag.id).join(',')`。因此不能把CgiGetDiss.tag为空直接认为无标签，否则mask95会清掉标签；建议改名用官网uniform_get_Dissinfo读取编辑元数据，或保留CgiGetDiss.vec_tagid。不要把tag对象序列化成[object Object]，也不要用label代替id。

官网默认封面常量准确值：`https://y.qq.com/mediastyle/music_v12/extra/default_300x300.jpg?max_age=2592000`。初始化 `cover:r.picurl||default`、`cover2:r.picurl2||default`；提交只在与该常量完全相等时发送空字符串，否则保留cover原值。若本地只为改名，直接保留fresh原picurl/picurl2即可；不要拿本地代理封面URL替换上游URL，不要任意把其他“默认样式”URL改空。

## 对实现方案的复核

严格creator.musicid + owndir=1 +当前账号关联，拒绝201..206；首次私密创建并readback dir_show=2；只在名称变化时用fresh完整元数据mask95编辑；缺字段拒绝；QQ端顺序为准——该方案总体与本次可证实接口一致，但标签读取须处理上面两个方法的差异。注意name最多20是JS string.length（官网校验），先trim再校验但原函数并未写回trim变量到state；本地可统一trim后上传。

实质剩余风险仍是Web写通道80105；解析data.retCode时可拒绝显式非0，但EditPlaylist尚无真实响应样本，不宜凭空要求一定存在retCode。全字段编辑缺tag/picurl2等时拒绝可避免毁损。顺序按QQ端为准时，读回歌曲集合/类型核验不能错误要求与本地有序数组逐项相等。
