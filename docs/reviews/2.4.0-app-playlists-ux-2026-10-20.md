# 应用歌单界面与易用性历史评估

评估日期：2026-10-20。本文归档自本地界面评估报告，记录当时的实现与发现，不代表当前 dev 的未修复问题清单；其中代码行号、验证数量和后续决策均保留原评估时的含义。后续实现与验收以当前代码及相关记录为准。

方法：双独立评估（A：/root/playlist_ux_review；B：/root/playlist_ui_evidence），主代理补充入口追踪与当前界面检查。

本轮评估应用歌单的入口、易用性、界面和使用逻辑，不修改业务代码。事实依据为当前源码；当前源码浏览器预览实看了我的库首次使用和新建弹窗。历史 Electron 截图只作辅助，不能代替现行版本实机验收。

## 结论

应用歌单作为独立于平台红心、平台歌单和临时播放队列的跨来源收藏，产品方向合理。日常列表中的单曲加入较方便；集中整理时的入口发现、批量选择器一致性和刷歌/队列覆盖仍有缺口。优先修正反馈真实性与收藏权限，随后补场景和统一操作，不需要重做整套视觉。

## 当前加入入口

| 位置 | 加入方式 | 范围 |
|---|---|---|
| 歌曲搜索结果 | 行内悬停＋、右键菜单 | 单曲 |
| 歌手页热门歌曲、全部歌曲 | 行内悬停＋、右键菜单 | 单曲；不可播放行受限 |
| 平台歌单、专辑及平台收藏列表详情 | 行内＋/右键；标题更多；多选操作条 | 单曲、完整集合、所选歌曲 |
| 搜索结果各分区 | 分区更多、多选 | 当前歌曲结果；展开所选专辑/歌单内曲目 |
| 我的库最近播放 | 行内＋、右键 | 单曲；没有该列表整批入口 |
| 我的库本地音乐、离线音乐 | 行内＋/右键、列表更多、多选 | 单曲、列表、所选歌曲 |
| 应用歌单详情 | 行内＋/右键、多选 | 复制单曲或选中歌曲到另一应用歌单；没有直接整份加入入口 |
| 主播放栏、歌词页播放控制 | 当前曲目加入按钮 | 当前歌曲 |
| 漫游 | 生成结果自动保存成应用歌单；已打开列表行内＋/右键 | 新建完整漫游结果或加入单曲 |

选择目标时均支持新建并加入；我的库新建应用歌单只创建空歌单，不是加入歌曲。全局 TrackRow 的覆盖不应泛化为所有显示歌曲的地方：刷歌、队列、预览弹窗使用各自结构。

直接入口缺口：刷歌卡片只有平台喜欢，且 App 在刷歌页隐藏主播放栏；播放队列只有播放/下一首/移除/排序；歌单预览需要先进入详情；迷你播放器没有应用歌单入口。这些场景用户仍可绕回其他页面，但不能就地完成收藏。

## 界面与交互评价

- 页面有明确的播放主操作；管理和危险操作放入更多菜单，来源和不可播放数量靠近列表。首次使用主按钮、名称输入和取消/保存关系清楚，符合现行 DESIGN.md 的克制方向。
- 快速加入仅需点击＋再点击歌单，记住最近目标，标明已包含并禁用，支持就地新建。播放栏按已加入数量点亮。适合连续收藏到同一歌单。
- 来源按 source:id 去重；相同歌曲跨平台版本会分别保留，不做未经用户确认的同曲合并。网易云、QQ、Apple、本地都能收藏；应用存档不改平台歌单，收藏不是下载，也不是播放队列。
- 不可播放歌曲在存档中保留；播放按可用性过滤，并区分平台停用、登录失效、本地文件丢失。保存已有元数据无需平台在线，展开整份在线歌单仍需相应平台可用。

## 五项优先问题

1. P1：批量移出失败仍提示成功。AppPlaylistPage.tsx:135、142 在 edit 捕获保存异常后继续清选择/发成功提示；edit 见 :161。遇到空间不足等情况，用户会收到互相矛盾的状态。建议仅在落盘成功后清选择并提示；失败保留选择。可用 impeccable harden 处理。
2. P2：不可播放与不可收藏错误耦合。TrackRow.tsx:95、114 整行 disabled 并隐藏＋；AppPlaylistPage.tsx:209、SearchPage.tsx:274 等触发，而 batch-tracks.ts:14 明确保留不可播收藏。建议将播放禁用与整理权限分开。可用 impeccable harden 处理。
3. P2：发现歌曲时有入口断点。ShuangeCard.tsx:173 只有平台喜欢，App.tsx 的刷歌条件隐藏主栏；QueuePanel.tsx:150、PlaylistPreviewModal.tsx:100 为专用行，均没有应用歌单动作。建议先补刷歌和队列的就地加入，再按使用频率考虑预览与迷你条。可用 impeccable onboard/clarify 处理。
4. P2：加入选择器分裂，目标页缺乏主动添加起点。TrackActionLayer.tsx:84 支持最近目标和重复标记；AppPlaylistDialog.tsx:79 使用原始顺序，没有搜索和重复状态，成功文案不含目标名，也不显示待加入数量；更多列表时需逐项找。AppPlaylistPage.tsx:291 空态仅说明去其他位置加入。建议统一排序、选中上下文和结果文案，空态提供去搜索的明确动作；歌单多时再增加搜索。每次只加入一目标是可接受的默认，无须一开始引入多目标提交。可用 impeccable clarify/onboard 处理。
5. P2：单曲移出没有撤销。AppPlaylistPage.tsx:211 行尾×立即持久化，批量则确认；没有撤销和成功反馈。建议提供短时撤销，而非每次弹确认。可用 impeccable harden 处理。

## 次要观察

行内＋默认隐藏（TrackRow.module.css:121），首次发现依赖悬停/空态说明；无需把所有操作常驻，可先强调当前悬停行并统一图标语义。“收藏”标签、平台红心和应用歌单并列，首次使用需要明确平台归属。批量加入常驻能力介绍与 DESIGN.md 的已有目标弹窗文案原则存在偏差。禁用行 opacity:0.52 可能使曲名和恢复原因过淡，需在实机深浅主题确认；不依据历史截图认定当前对比度不达标。长曲名/歌手省略后缺完整提示。未把键盘导航列为缺陷：项目现行规范和全局拦截明确只支持鼠标普通控件。

## 认知负担与用户旅程

首次用户：在我的库能理解跨来源用途，但新建后只有空态说明，需要记住提示再去找歌；刷歌“喜欢”容易被误当应用收藏。高频收藏者：普通行两次点击可完成，最近目标减少查找；切换到批量选择器需要重新适应顺序，多歌单无搜索。集中整理者：来源筛选、不可播放原因和多选有帮助，但单曲误移出无法恢复，保存失败出现成功提示会破坏信任。

认知负担总体中等，主要在入口回忆和一致性。我的库有6—7个分类，批量模式动作较多；需要检验真实使用中的扫描成本，不能仅凭超过四个选项判为不可用。
