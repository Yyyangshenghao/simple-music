# 2.4.0 共用虚拟列表滚动优化

目标 `dev/2.4.0`，基准 `899fd07`；工作分支 `feature/scroll-render-performance`。不升级版本或发布。

## 原因与修改

用户反馈多数页面上下滚动卡顿。共用 `VirtualList` 虽然限制了挂载行数，但每次可视区间变化仍调用所有可见行的 `renderRow`，让未变化歌曲行重复执行组件、store selector 和 React 开发检查。CPU 采样中可见 JSX 创建、属性校验及组件协调的开销。

新增默认浅比较的 `VirtualRow`，以行下标、行高、`renderRow` 引用作为输入。列表自己的滚动更新复用未变行；父级传入新渲染函数时更新内容和事件闭包。没有自定义比较器，行内 context 和外部 store 订阅仍正常更新。全部 9 处调用覆盖歌单、曲库、艺人、漫游、应用歌单及播放队列，DOM 层级、行高、滚动查询节流和视觉效果保持原行为。

## 对照测量

macOS、Apple M5 / ANGLE Metal，真实 Electron 开发窗口、独立 userData。5,000 首无封面本地测试歌曲，1536×864 CSS 视口、DPR 2，动态背景开启；CPU Profiler 开启时，连续 240 个动画帧按每帧 110px 往返滚动。两侧使用相同环境和滚动序列，各测一轮。数值为帧间隔，不是整轮任务耗时。

| 条件 | 修改前平均 / P95 | 修改后平均 / P95 |
|---|---:|---:|
| 原速 CPU | 5.88 / 6.30ms | 5.88 / 6.50ms |
| DevTools 4 倍 CPU 限速 | 12.82 / 17.90ms | 6.55 / 11.90ms |

原速两侧均无超过 25ms 的帧；限速前 1 帧超过 25ms，修改后 0 帧。该结果说明减少了慢 CPU 条件下的渲染开销，不代表所有机器或页面有固定帧率增益。测量终点均挂载 33 行。

另外对设置页以真实 wheel 输入检查全局效果：1280×800 视口，100 次上下滚轮，每次间隔 16ms；原速及 4 倍 CPU 限速下，三种背景/透明度组合均无超过 25ms 的帧。原速开启背景与毛玻璃时，GPU 进程 CPU 时间 / 墙钟时间约 40%，关闭两者约 24%；这不是 GPU 硬件利用率。可确认装饰效果增加合成开销，但本机没有复现它们导致的掉帧，因此没有改变用户视觉偏好或添加滚动时切换效果的逻辑。

## 回归与界面

先在旧实现运行 [Electron 回归脚本](checks/virtual-list-scroll.cjs)：连续滚动 10 行时，始终可见行被重复渲染 11 次，断言失败；修改后 0 次。脚本还验证滚动 context 启停、外部播放状态更新、父级可见文本和点击闭包更新、第 5,000 行可达、挂载行数有界、列表缩短及行高变化。连接与临时 React root 均在 finally 中清理。

在环境已提供 Playwright 的情况下运行；无需将 Playwright 加入应用依赖：

```bash
npm run dev -- --remote-debugging-port 9341 -- --user-data-dir=/tmp/simplemusic-scroll-regression-profile
# 另一终端；Playwright 不在默认解析路径时，通过 NODE_PATH 指向现有工具运行环境。
node docs/reviews/checks/virtual-list-scroll.cjs
```

真实界面用完整 Track 测试资料验证：搜索末曲后点击保留完整 5,000 首队列与原始下标 4,999；多选可更新；深浅主题在 1280×800、960×600 均能滚到末尾；5,000 首队列打开后直接显示当前末曲，行数有界，无页面错误。队列点击使用捕获函数检查参数，播放状态使用隔离 store 资料，不宣称真实音频播放通过。
