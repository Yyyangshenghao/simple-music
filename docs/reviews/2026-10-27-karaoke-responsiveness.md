# 伴奏生成期间界面卡顿修复

用户反馈生成时整个界面的操作、滚动和动画变卡。本轮在真实设置页、流体背景及持续滚轮输入下复现：空闲动画帧间隔 P95 约 6.4 ms，生成时升至 29.4 ms。主界面未观察到超过 50 ms 的 JavaScript long task；原生推理每块约 472 ms，连续处理 32 块。证据指向共享 GPU 的持续争用；隔离进程及上一轮降低 RSS，并不保证前台流畅。

## 修复与取舍

分离 Worker 在下一块真正提交推理前等待空档。空档按上一块推理往返耗时的三倍计算，限制在 100–1500 ms；逆变换、写盘和下一块前处理计入空档，不额外重复等待。最后一块完成后直接保存，不多等一次。原生与浏览器 WebGPU 共用该调度；不修改模型、精度或音频处理。

空档开始前上一块张量已释放，不增加整首缓冲。等待结束后先检查取消，不再启动新推理。公开队列的取消仍立即终止辅助实例，不等待计时器；直接使用 Worker 的取消最多等待当前空档。每次任务单独计算下一次提交时刻，不影响重试或下一首。

辅助实例通过 [Node.js 官方优先级接口](https://github.com/nodejs/node/blob/main/doc/api/os.md#ossetprioritypid-priority) 将自身设为 `PRIORITY_BELOW_NORMAL`；失败只告警。该设置不改变播放器主进程优先级。保留隐藏渲染页原有启动开关，避免在已降低实例优先级后被 Chromium 再额外降级。

这轮明确用生成速度换交互响应，后台任务不再持续追求最大吞吐。没有降低内存保护门槛，也没有承诺 GPU 占用硬上限。

## 实际对照

Apple M5、32 GiB、macOS arm64、Electron 42.11.0+wvcus、ONNX Runtime 1.30.0，HQ3 半精度。实际主窗口为 1600×1000，设置页使用均衡流体背景，持续输入滚轮事件；测试入口关闭失焦暂停及主窗后台节流，保持窗口失焦时负载持续。输入为主歌片段重复组成的 180 秒、44.1 kHz 双声道 PCM16 WAV，32 块；模型预装，各轮使用独立资料与保存目录。

| 方案 | 生成帧间隔 P95 | 超过 25 ms 帧/秒 | 超过 50 ms 帧/秒 | 生成耗时 |
| --- | --- | --- | --- | --- |
| 修复前连续推理 | 29.4 ms | 6.23 | 0.456 | 19.76 s |
| 仅降低优先级并恢复渲染页自动降级 | 23.5 ms | 4.26 | 0.236 | 33.84 s |
| 上述方案加固定 400 ms 休息 | 17.7 ms | 2.92 | 0.138 | 43.46 s |
| 原优先级加固定 900 ms 休息 | 17.6 ms | 2.80 | 0.103 | 48.64 s |
| 最终后台调度 | 11.8 ms | 2.41 | 0.064 | 62.67 s |

最终超过 50 ms 的帧频率下降约 86%，超过 25 ms 的帧频率下降约 61%。最大帧间隔从 82.3 降至 58.9 ms，仍有偶发尖峰；不等于所有硬件始终满帧。最终用时约为原来的 3.2 倍，不能只报告流畅度收益而省略这一成本。长帧按生成总时长归一化，不能直接把不同用时的帧数量比较为降幅。

五轮 180 秒输出均为 31,752,044 字节，逐字节一致，SHA-256 为 `39722b0722fd4a51fa8b7b54685e1c17e065ad7d5fa69d5bfad79f021d263df3`。实际界面见[设置页滚动截图](assets/2026-10-27-karaoke-responsiveness/actual-settings-scroll.png)，逐轮汇总、长帧时序和推理时序见 [measurements.json](assets/2026-10-27-karaoke-responsiveness/measurements.json)。

原开发实例未停止。为允许独立测量实例通过准入，只有测量入口将预留计算使用的总内存模拟为 16 GiB；真实空闲、可回收内存未改，生产预算代码未改。本轮不用于证明内存准入、低内存性能或内存峰值收益。未进入推理、无有效帧采样的预热记录不参与上述对照。

## 验证

- 两条回归用例先在修复前失败，修复后通过：连续推理必须让步；空档中取消不得启动下一块并清理临时输出。
- 类型检查通过；全量 370 个文件、3461 项测试通过；独立只读复核通过。
- 真实辅助实例在第一块结束后的空档中取消，约 54 ms 后退出；立即重新入队成功生成，未发布被取消的成品。
- 强制原生初始化不可用的真实浏览器回退完成 12 秒、3 块生成，与原生重试结果逐字节一致（2,116,844 字节，SHA-256：`d35bffb97618129b170497fc60ebfa0ee6f01fcef1ef8f00dda28f5f588f12c2`）。
- 本轮未制作安装包或重跑生产构建，已使用实际 `npm run dev` 验证当前入口、辅助进程和 Worker。Windows 实机及更重的歌词/壁纸场景仍需对应验收，单块内部及模型初始化仍可能有短暂尖峰。

## 后续修复：内存准入误拦

用户随后反馈任务长期停在“当前内存不足，等待释放后继续”。队列重试正常，但旧规则在模型、音频、512 MiB 辅助预算之外，额外预留 `max(1 GiB, 总量×12%)`。32 GiB 设备光额外预留就有 3.84 GiB，HQ3 三分钟任务合计要求 6.06 GiB；本机初始探针可用 5.39 GiB，原规则会一直拒绝。

现将额外预留限制在 1–2 GiB，HQ3 同任务要求降为 4.22 GiB；模型预算、音频长度预算、低内存拒绝和运行时停止保护保留。API 与辅助进程继续共用同一公式。补充覆盖 32/64/128 GiB 误拦、实际不足时拒绝、长音频额外预算，以及等待任务可用内存恢复后自动重试。

这次验证完全使用真实内存数据，没有沿用前述测量入口的模拟总量：独立应用启动后资源接口报告可用 4.73 GiB，允许启动；实际完成 180 秒 HQ3 标准生成，耗时 67.08 s，成品 31,752,044 字节。类型检查及全量 371 个文件、3471 项测试通过。原始结果见 [admission-check.json](assets/2026-10-27-karaoke-responsiveness/admission-check.json)。
