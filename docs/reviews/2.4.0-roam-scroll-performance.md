# 2.4.0 漫游排序与滚动查询优化

目标分支：`dev/2.4.0`，基准 `08932e2`；工作分支 `feature/roam-scroll-performance`。不升级版本或发布。

## 问题与改动

漫游保存只删除、添加曲目，没有调用显式排序；现在添加成功后按预览的完整序列调用 `song_order_update`，失败则停止保存流程。合作曲按来源和 ID 去重，使本地预览与远端不允许重复歌曲的序列一致。排序写前核对本人普通歌单、完整 ID 集合及 Cookie，拒绝中途换号或外部修改。

上游参数核对了安装依赖的 `module/song_order_update.js` 与 `public/docs/home.md`；[上游接口说明](https://binaryify.github.io/NeteaseCloudMusicApi/#/?id=调整歌曲顺序)。

“播放器正在处理较多操作”来自 `PLAYBACK_BUSY`：后台在途命令上限为 128。旧版滚动不仅连续补曲目详情，还会在每行挂载时调用红心和离线查询；隔离对照窗口复现了后台队列繁忙。

共用虚拟列表仍即时更新可见行；滚动停止 180ms 后再补最终区段，同时暂停滚动中的行查询及骨架动画。详情失败窗口冷却 30 秒，搜索/手动刷新仍可主动重试，失效会话不写入失败冷却。漫游结果也改用虚拟列表，保留完整播放队列及歌曲下标。

## 实测

真实 macOS Electron 开发窗口、独立 userData，870 首 API 测试资料。内容视口 1280×800；滚动用 100 个连续动画帧从顶部移至底部，起始 100 首详情已加载。前后使用同一最小动效预设，API 资料同时覆盖主界面与独立播放后台，统计从初始查询完成后开始。

| 项目 | 修改前 | 修改后 |
|---|---:|---:|
| 快速滚动中的详情请求 | 8 | 0 |
| 滚动及停止后的详情请求总数 | 8 | 1（最终第 8 窗口） |
| 红心查询涉及 ID 数 | 384 | 21 |
| 离线状态批次 | 105 | 3 |
| 末尾挂载行数 | 21 | 21 |

最小动效前后均未出现超过 50ms 的帧间隔，不能据此声称消除所有卡顿或提高固定比例的帧率。关闭对照应用后补测修改版标准动效，仍为滚动中 0 次、停止后 1 次详情请求，无页面错误；该次离线状态已缓存，批次数不用于前后比较。

360 首漫游结果在真实窗口首尾均挂载 22 行；两类行查询开启且缓存为空时，所观测在途峰值 44，无 `PLAYBACK_BUSY`。点击末曲后后台队列仍为 360 首、下标 359、对应 ID 正确。截图：[870 首末尾](assets/2.4.0-roam-scroll-performance/playlist-bottom.png)、[漫游末尾](assets/2.4.0-roam-scroll-performance/roam-bottom.png)。[机器记录](2.4.0-roam-scroll-performance-verification.json)。

类型检查、262 个文件 / 2,271 项测试及独立复核通过。回归覆盖排序与拒绝写入边界、失败传播、合作曲去重、连续滚动只通知最终区段、短列表切换、卸载计时器清理、失败冷却及停用后恢复。

未执行真实网易云账号写入；排序接口由服务与路由回归验证。未在 Windows/Linux 实机复测，也未把模拟 API 的帧间隔作为网络、音频或 GPU 性能保证。
