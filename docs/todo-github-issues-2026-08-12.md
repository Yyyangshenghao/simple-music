## [#2 使用 QQ 音乐作为音源时，歌词与歌曲不匹配](https://github.com/Yyyangshenghao/simple-music/issues/2)

- 提交者：LSkittles
- 创建时间：2026-08-07 20:06（Asia/Shanghai）
- 用户反馈：QQ 音源下歌词与当前歌曲不匹配；提交者推测歌曲 ID 处理可能有误。
- 缺失信息：具体歌曲、入口（搜索/歌单/专辑等）、错误歌词对应的歌曲、是否稳定复现。

### 初步代码评估

已确认的代码事实：

- QQ 曲目映射同时保留字符串 `mid` 与数值 `qqId`，其中领域对象的 `id` 通常被设置为 `mid`。
- `src/hooks/useLyricsFetch.ts` 请求歌词时传入 `mid = track.songmid || track.mid`，同时传入 `id = track.id`。对 QQ 曲目而言，后者通常仍是 `mid`，而不是 `qqId`。
- `server/lib/qq-client.ts` 会删除 `id` 中的非数字字符并把剩余数字作为 `songID`。
- `src/lib/qq-music-service.ts` 也使用 `track.id` 作为歌词请求的 `id`，标识选择规则并未统一。

待验证假设：

- 如果字符串 `mid` 恰好包含数字，当前逻辑可能生成一个无关的数值 `songID`；请求同时携带正确 `songMID` 和错误 `songID` 时，上游可能按错误 ID 返回歌词。
- 即使只发送正确 `songMID`，错配也可能来自上游选择规则、曲目映射、缓存或切歌竞态，不能在复现前排除。

初步判断：标识混用是**值得优先验证的高可信线索**，尚不能视为已确认根因。

### 已实施修复

- `songMID` 只取 `mid/songmid`，`songID` 只取真实 `qqId`；没有真实 `qqId` 时不发送 `songID`。
- 服务端仅接受纯数字 `songID`，不再从字母数字混合的 `mid` 中抽取数字，避免两个标识指向不同歌曲。
- 如果对照测试证明只传正确 `songMID` 仍会错配，继续检查歌词请求缓存、不同曲目映射入口和切歌异步竞态。

## [#3 歌曲音质选项设计问题](https://github.com/Yyyangshenghao/simple-music/issues/3)

- 提交者：LSkittles
- 创建时间：2026-08-07 21:49（Asia/Shanghai）
- 用户反馈：QQ 音源下，默认音质为“最高”时，部分歌曲无法播放；手动切换到 FLAC 后可播放。示例为徐珊《夜微凉》。梦然《大眼睛》在各音质下均无法播放。用户建议无法恢复时自动跳过。
- 缺失信息：应用版本、登录/VIP 状态、地区、完整日志、两首歌的 `mid/mediaMid/qqId`、实际 HTTP 状态或媒体错误码。

### 初步代码评估

已确认的代码事实：

- `server/lib/qq-client.ts` 在 `max` 模式按 Hi-Res FLAC → 无损 FLAC → 320k MP3 → 128k MP3 → AAC 生成候选，并直接选择第一个 `purl` 非空的结果；没有验证该流地址是否真的可访问。
- `src/lib/audio-engine.ts` 监听了 `waiting/playing/pause/ended`，但没有监听媒体 `error`；加载失败后状态可能长期停在“加载中”，也没有触发低音质重试或下一首。
- `src/lib/track-preload.ts` 解析 QQ 播放地址时没有把曲目已有的 `mediaMid` 传给服务端，尽管服务端已经支持按 `mediaMid` 生成文件名候选。这可能降低部分歌曲的文件匹配准确率。
- 当前只会在“解析阶段没有 URL”时触发跨音源兜底；如果拿到了非空但不可播放的 URL，播放器层失败不会回到兜底流程。

仍需实测确认：

- 徐珊《夜微凉》是否稳定表现为 RS01 地址不可访问、F000 地址可访问。
- 梦然《大眼睛》是否确为版权/地区/VIP 限制（例如 104003），而不是 `mediaMid`、CDN `sip` 或登录凭证选择问题。
- QQ 返回的多个 `sip` 是否需要逐个尝试，而不是固定使用第一个。

初步判断：这不是单一“音质选项”问题，而是 **候选地址选择、媒体错误恢复、标识透传** 三段链路共同缺少闭环。

### 候选实现路径（待确认产品行为）

1. 先补媒体 `error` 的状态收敛、提示和可测试回调，避免无限“加载中”。
2. 正确透传 `mediaMid`，并为 QQ URL 请求候选顺序补测试。
3. 当 `max` 返回的高档地址实际加载失败时，在同一首歌内依次降档重试；全部失败后再走跨音源兜底。
4. 只有同曲降档和跨源兜底均失败后，才考虑自动跳过。自动跳过应设置次数上限，避免整队列连续失败形成循环。

以上路径需先确认失败时是否允许自动降档、跨源和跳过；未确认前不视为既定需求。

## 联合评估结论

- 2.0 已立项为多平台融合架构，目标设计见 [Simple Music 2.0 多平台融合架构设计](./specs/2026-08-12-simple-music-2.0-multi-provider-design.md)。#2 仍可在 1.x 独立修复；#3 的媒体错误收敛可先做最小修复，完整的音质候选与多音源降级纳入 2.0 播放解析阶段。
- 建议先处理 #2，再处理 #3。#2 的改动面更集中，容易用明确标识规则和回归测试封闭；#3 涉及服务端 URL 解析、渲染层媒体事件、重试与队列策略，风险更高。
- #3 不建议直接从“自动跳过”开始。优先让同曲降档和跨源兜底真正覆盖媒体加载失败，自动跳过只作为最终策略。
- 开始修复前，最有价值的补充材料是：#2 的一首稳定复现歌曲，以及 #3 两首示例歌曲在当前分支上的请求/媒体错误日志。
